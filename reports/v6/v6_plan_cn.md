# V6 候选修复与候选选择实验

固定基线为 V4b 的 contract_v4 控制器与 onpolicy_v001/epoch_02 适配器，已有相同入口的 CPU 验证 92/120（e50）与公开测试 184/240（e42）。本轮不增加工具或模型调用预算。

1. 从同一基线适配器分别训练两份 LoRA，一份用真实失败轨迹与经训练评分验证的 SQL 做修复监督，一份用同题中公开示例匹配而三实例结论不同的候选做选择监督。混入普通训练样本。两臂各训练一次，不根据本轮验证反馈选择训练轮数。
2. 在构建本轮数据前，按训练集数据库划出增量留出组。原始适配器曾用过官方训练集，留出结果只用于诊断本轮更新。对基线和两种新权重运行同一道题一条贪心轨迹的留出评测。只向推理程序提供官方公共工具；三实例评分单独在推理后完成。
3. 固定 contract_v4、seed=42、4 次生成、每次最多 384 个新 token、8 次计费工具。用官方预测和评分入口做完整 120 题四线程 CPU 验证。报告三个实例均正确的题数、至少检查到一条正确 SQL 的题数、存在正确候选时选中率、相对基线的修对/改错和运行成本。
4. 若有候选 CPU 验证超过 92/120，且增量留出集最终正确数不低于基线，从合格者中按 CPU 验证正确数、留出正确数、CPU 验证生成次数较少、最后名称字典序选一份权重，记录哈希与配置后仅评测该候选的完整公开 test。缺少跨两组数据的一致收益时停止在验证阶段。仅当锁定候选在公开 test 超过 184 题时推荐替换默认；保留原始结果与所有负结果。两组监督实验均无可靠收益时不扩大 GRPO。
