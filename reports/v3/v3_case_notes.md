# 第三轮案例与结果边界

第三轮测试182/240，v2为181/240。逐题比较只改善1题、没有退步；同一单种子和固定划分上的小幅变化，不代表SQL推理能力出现明显提升。本轮没有更新模型权重。

## 唯一改善题

`test-a0a87f31df47b1b8`：How many shops are there in each location?

v2提交 `SELECT Location, COUNT(*) AS count FROM shop GROUP BY Location`；本轮提交 `SELECT COUNT(*), LOCATION FROM shop GROUP BY LOCATION`。

两者都按地点统计商店数，关键差异是输出列的顺序：本题要求数量在前、地点在后。原方案列顺序错误，本轮修正后在三个实例全部通过。这里不是新增了复杂聚合或连接能力。该题属于v2预算未尽就回退的失败题，第三轮恢复后救回。

## 恢复成功不等于修复成功

测试中32次立即恢复，11次随后提议通过协议保护；这不意味着修好了11道题。最终相对v2只有1题从错变对。重复提议从54次增加到63次，公开匹配但最终错误仍是28题。

预算未尽回退提交由10题降至2题，但其中一部分路径只是多生成一次后耗尽额度，再执行原回退。不能用该计数下降代替全实例成绩。仍有2题在有剩余生成和工具预算时回退，且都失败。

## 六次生成为何没有选中

两组验证均89/120，逐题对错集合完全相同。六次组比四次组多35次模型生成、30次重复提议，29次恢复中只有3次新提议被接受。因此按预定的并列规则选择四次组；没有根据测试结果改变选型。

## 更有价值的下一步

优先在train中采集当前策略的真实错误与拒绝状态，监督模型完成“识别错误→修改SQL→再验证”的动作序列，补充有明确用途的execute/retrieve示例，并训练正确候选的选择。旧构造脚本需先适配JSON动作与动态候选数量，再考虑增加生成上限。validation用于选型，test案例只用于报告分析。
