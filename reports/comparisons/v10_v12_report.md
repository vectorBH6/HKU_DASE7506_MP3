## V12 的两道增益

V12 沿用 V9 的 Qwen3-0.6B 和 V7 LoRA。只有准备提交的那条 SQL 已经收到真实的公开检查失败反馈，并且还有工具预算，才尝试文本条件修复。候选包括忽略大小写、包含匹配，以及根据题目和表结构修正名称条件。新候选通过公开检查后才会替换原答案。测试中有 26 题符合启动条件，11 题实际产生了可检查的候选，额外 18 次检查最终改动了 2 个答案。两题均通过三个实例。V12 对每道题的模型提示和生成都与 V9 一致。[实现](../../submission/v12_v9_fallback.py) · [修复逻辑](../../submission/v11_text_fallback.py) · [逐项对照](../../runs/e120_v12_v9_fallback_replay/test/r001/replay_summary.json)

V10 和 V11 在各自看到测试分数前封存。V12 在取得 V10 测试结果后，依据该修复在 V9 完整验证上从 98 到 99、改错 0 题的记录单独封存。先复用 V9 的真实 CPU 模型输出，通过 V12 工厂重新执行官方工具和评分，再从头运行 V12。新推理与重放的完整验证轨迹 120/120 一致、测试轨迹 240/240 一致。V12 正式测试使用 4 个 CPU 线程，预测 90.6 分钟，评分约 6.5 秒，预测进程树峰值 3.97 GiB。总工具调用 1,119 次，单题最多 8 次。模型生成 596 次，单题最多 4 次。Codex 协助实现、运行与分析。[V12 冻结记录](../v12/v12_replay_lock.json) · [正式验证](../v12/v12_official_validation.json) · [正式测试](../v12/v12_official_test.json)

## 下一轮值得解决的问题

在 V12 验证剩下的 21 道错题中，只有 5 道曾检查过正确 SQL 却选错。其余 16 道从未查到正确 SQL，其中 9 道只查到能通过公开示例的错误 SQL，7 道连公开示例也没有匹配。若继续开发，可从官方训练库中抽取同类真实失败，标注参考答案所用的实体、连接路径和聚合层级，训练专门生成局部 SQL 修复的候选生成器。先在留出的数据库上衡量有多少原先无正确候选的题首次产生三实例正确的 SQL，再比较实际选中数和改错数。[V12 候选覆盖](../v12/v12_validation_coverage.json)

本轮已有几项负结果界定了这个方向。用 V10 自己的 480 道训练轨迹和 779 个已过公开检查的候选重训选择器，完整验证从 100 降到 97。用 279 道训练题做单 LoRA 教师蒸馏，在同一 GPU、同一路由的开发验证上从 98 降到 95。跨表联合修复在 98 道留出训练题上实际多修 1 道，在 V12 完整验证中净增 0 道；把外键检查提前到还有工具预算时，9 个首选候选仍未通过公开示例。这些版本均未进入公开测试。[实际训练轨迹的选择器](../../runs/v10_onpolicy_chooser/results.json) · [蒸馏对照](routed_distill_validation.json) · [外键修复的训练留出](../../runs/v13_fk_paths/train_holdout.json) · [提前检查的验证结果](../../runs/v13_fk_paths/early_validation.json)

## 复现当前最好版本

在项目根目录使用本地基础模型、冻结的 V7 LoRA 及现有虚拟环境。脚本按冻结哈希打包学生入口，然后调用原样的预测器和评分器。以下为本轮实际使用的 CPU 核心偏移。

```bash
.venv/bin/python -B scripts/run_v12_fresh.py --split test --cpu-offset 8
.venv/bin/python -B scripts/run_v12_fresh.py --split validation --cpu-offset 0
```
